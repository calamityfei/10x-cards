# API Endpoint Implementation Plan: POST /generations

## 1. Endpoint Overview

This endpoint logs the summary of an AI generation event after a user has reviewed flashcard candidates. It creates a single record in the `generations` table that tracks metrics such as the AI model used, generation duration, source text characteristics, and user decisions (accepted unedited, accepted with edits, or deleted cards).

This is a transactional endpoint called after the user completes their review of AI-generated flashcard candidates. The returned `generation_id` is then used when saving the accepted flashcards via the `POST /flashcards` endpoint.

## 2. Request Details

- **HTTP Method**: POST
- **URL Structure**: `/api/generations`
- **Authentication**: Required (JWT via Supabase Auth)
- **Content-Type**: `application/json`

### Parameters

**Required (in `generation_log` object):**

- `source_text_length` (integer): Character count of original source text. Must be between 1000 and 10000.
- `generated_count` (integer): Total number of flashcards generated by AI. Must be >= 0.
- `accepted_unedited_count` (integer): Number of cards accepted without modifications. Must be >= 0.
- `accepted_edited_count` (integer): Number of cards accepted after user edits. Must be >= 0.
- `deleted_count` (integer): Number of cards rejected/deleted by user. Must be >= 0.

**Optional (in `generation_log` object):**

- `model` (string): AI model identifier (e.g., "anthropic/claude-3-haiku"). Max 100 characters.
- `generation_duration` (integer): Time taken for AI generation in milliseconds. Must be > 0 if provided.
- `source_text_hash` (string): SHA-256 hash of the source text. Must be exactly 64 characters if provided.

### Request Body Example

```json
{
  "generation_log": {
    "model": "anthropic/claude-3-haiku",
    "generation_duration": 1450,
    "source_text_hash": "a1b2c3d4e5f6...",
    "source_text_length": 1200,
    "generated_count": 10,
    "accepted_unedited_count": 8,
    "accepted_edited_count": 1,
    "deleted_count": 1
  }
}
```

## 5. Data Flow

1. **Request Reception**: Astro API route receives POST request
2. **Authentication Check**: Verify JWT token exists and extract user_id from `context.locals.supabase.auth.getUser()`
3. **Input Validation**: Validate request body against Zod schema
4. **Service Layer Call**: Pass validated data to generation service
5. **Database Insert**: Service inserts record into `generations` table with authenticated user_id
6. **Response**: Return created generation log with 201 status

### Database Interaction

- **Table**: `public.generations`
- **Operation**: INSERT
- **RLS**: Automatically enforced - user can only insert their own records
- **Fields populated**:
  - `user_id`: From authenticated session (not from request body)
  - All fields from `generation_log` object
  - `created_at`: Auto-populated by database DEFAULT

## 6. Security Considerations

### Authentication

- **JWT Verification**: Must call `context.locals.supabase.auth.getUser()` to verify authentication
- **User ID Source**: MUST use `user_id` from authenticated session, NEVER from request body
- **Early Return**: Return 401 immediately if authentication fails

### Authorization

- **Row-Level Security**: Supabase RLS policies automatically enforce that users can only insert their own generation logs
- **Policy**: "Enable insert for own generation logs" checks `auth.uid() = user_id`

### Input Validation

- **Zod Schema**: Validate all inputs before database interaction
- **Type Safety**: TypeScript ensures type correctness at compile time
- **Range Checks**: Enforce database constraints in validation layer:
  - `source_text_length`: 1000-10000
  - `generation_duration`: > 0 (if provided)
  - All count fields: >= 0
  - `source_text_hash`: exactly 64 chars (if provided)
  - `model`: max 100 chars (if provided)

### Data Sanitization

- Supabase client handles SQL injection prevention via parameterized queries
- No user-provided data should be used in raw SQL queries

## 7. Error Handling

### Validation Errors (400)

- Missing `generation_log` object
- Invalid data types (e.g., string instead of integer)
- Out-of-range values:
  - `source_text_length` < 1000 or > 10000
  - `generation_duration` <= 0
  - Any count field < 0
- Invalid string lengths:
  - `model` > 100 characters
  - `source_text_hash` != 64 characters

**Handler**: Catch Zod validation errors, return 400 with descriptive message

### Authentication Errors (401)

- No JWT token in request
- Invalid or expired JWT token
- User not found in auth system

**Handler**: Check authentication early, return 401 with generic "Unauthorized" message

### Database Errors (500)

- Connection failures
- Constraint violations (shouldn't occur if validation is correct)
- RLS policy violations (shouldn't occur if user_id is from auth)
- Unexpected database errors

**Handler**: Log full error details server-side, return 500 with generic message to client

### Error Response Pattern

```typescript
return new Response(JSON.stringify({ error: "Error message" }), {
  status: 400,
  headers: { "Content-Type": "application/json" },
});
```

## 8. Performance Considerations

### Database

- **Single INSERT**: Operation is lightweight (one row)
- **Indexes**: `user_id` index exists for RLS performance
- **No Joins**: Simple insert with no complex queries

### Validation

- **Zod Performance**: Validation is fast for simple object structure
- **Early Returns**: Fail fast on validation errors

### Potential Bottlenecks

- None expected for this endpoint
- Database insert is O(1) operation
- No external API calls or heavy computations

## 9. Implementation Steps

### Step 1: Create Zod Validation Schema

**File**: `src/pages/api/generations.ts` (or extract to separate validation file)

Create schema matching `CreateGenerationCommand`:

```typescript
const createGenerationSchema = z.object({
  generation_log: z.object({
    model: z.string().max(100).optional(),
    generation_duration: z.number().int().positive().optional(),
    source_text_hash: z.string().length(64).optional(),
    source_text_length: z.number().int().min(1000).max(10000),
    generated_count: z.number().int().min(0),
    accepted_unedited_count: z.number().int().min(0),
    accepted_edited_count: z.number().int().min(0),
    deleted_count: z.number().int().min(0),
  }),
});
```

### Step 2: Create Generation Service

**File**: `src/lib/services/generationService.ts`

Implement service function:

```typescript
export async function createGenerationLog(
  supabase: SupabaseClient,
  userId: string,
  logData: CreateGenerationLogDto
): Promise<CreateGenerationResponseDto>;
```

Service responsibilities:

- Accept Supabase client, user_id, and validated log data
- Insert into `generations` table
- Handle database errors
- Return created record (without user_id)

### Step 3: Create API Route Handler

**File**: `src/pages/api/generations.ts`

Implement POST handler:

1. Add `export const prerender = false`
2. Implement POST function
3. Extract Supabase client from `context.locals.supabase`
4. Verify authentication via `supabase.auth.getUser()`
5. Parse and validate request body with Zod
6. Call generation service
7. Return 201 with created generation log

### Step 4: Error Handling Implementation

In the API route handler:

- Wrap logic in try-catch block
- Handle Zod validation errors → 400
- Handle authentication failures → 401
- Handle database/service errors → 500
- Log errors appropriately (console.error for server-side debugging)

### Step 5: Integration Points

After implementation, ensure:

- Frontend can call this endpoint after user reviews candidates
- The returned `generation_id` is available for subsequent `POST /flashcards` call
- Error messages are user-friendly and actionable
